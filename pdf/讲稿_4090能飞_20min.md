## 第 1 页 · 封面（1 分钟）

各位老师好，我是程仁龙，我们的项目叫「4090 能飞」。

这个名字改编自网络梗，但它说的是一件很实在的事：我们在**一张 RTX 4090** 上，从零实现了 Qwen3.8-27B 这个 270 亿参数模型的完整推理引擎。项目开始时，16K 长文的首 token 要等 **27 分钟**；提交时，这个数字是 **34 秒**。

[指飞行显卡] 今天我想讲清楚三件事：这张卡是怎么"飞"起来的，我们如何证明它飞得**对**，以及哪些地方它还飞不到——我们如实说明。

### 本页可能被问

**Q：27 分钟和 34 秒，是怎么测出来的？**
两个数字是同一个测试：给模型输入一篇 16384 个 token 的长文（大约两三万字），再让它生成 128 个 token，计时"从发出请求到收到第一个字"——这个指标叫 TTFT（Time To First Token，首 token 延迟）。27 分钟（1635 秒）是我们第一个"功能全对但没优化"的版本，34.6 秒是最终版本按正式规程测的：先跑 1 次热身，再测 5 次取中位数。同一张卡、同一个模型、同一个输入，只有代码优化不同，所以可以直接比。

**Q：一张 24 GB 的卡怎么装得下 270 亿参数？**
两个原因。第一是量化：权重用 4 比特整数存（W4A16 格式），270 亿参数只占约 13 GB，加上少数保持 BF16 的模块，常驻约 19.5 GB。第二是这个模型的架构特殊：64 层里有 48 层是"线性注意力"（GDN），它不需要随文本变长而增长的 KV 缓存，状态是固定大小的；只有 16 层是传统注意力需要存 KV。所以哪怕 16K 长文，显存峰值也只有 19958 MB，没超 24564 MB 的上限。

## 第 2 页 · 从零开始（1.5 分钟）

先讲清楚起点和难度。starter 仓库里**没有任何现成实现**——没有这个模型的结构代码，没有 W4A16 量化算子，没有 HTTP 服务，全部要自己建。

这个模型的结构比常规 LLM 麻烦：[指层叠图] 64 层不是清一色的注意力，而是**每四层里三层 GDN 线性注意力、一层全注意力**，这样的组合重复 16 组。两类层的请求状态完全不同——GDN 层要维护因果卷积的环形缓冲和 FP32 递归状态，全注意力层是 24 个查询头配 4 个 KV 头、head_dim 256，还有输出门控和只作用于前 64 维的部分 RoPE。

[指矩阵图] 量化格式是 W4A16：权重 4 比特、每 32 个一组共享缩放系数和零点；但只有投影矩阵是 4 比特，卷积、归一化这些还是 BF16——逐模块混合，不能一套算子通吃。

[指清单] 同时合同有硬约束：只许用这一张卡、禁止任何 fallback；评测文件一律不动；不许按测例特判；health 接口必须真实——能力没验证过就必须报 false。

### 本页可能被问

**Q：GDN 到底是什么？和普通注意力有什么区别？**
GDN 全称 Gated DeltaNet，属于"线性注意力"这一类。普通注意力生成每个新字时，要回头看之前**所有**字的 Key/Value 缓存，所以显存和计算都随长度增长。线性注意力不存历史，而是把历史"压缩"进一个**固定大小的状态矩阵**里，每来一个新字就更新一次这个状态（数学上像 RNN 的递归），再配一个短窗口的因果卷积捕捉近距离信息。好处是长文本时显存和每字计算量都不涨；代价是状态更新的数值精度敏感，所以我们的递归状态用 FP32 存。这个模型 48 层 GDN + 16 层全注意力混着用，兼顾效率和精度。

**Q：为什么量化不能统一成 4 比特？**
量化方案是模型发布方决定并烘焙进 checkpoint 的，不是我们选的。他们用 AWQ 方法只把大的投影矩阵（占体积绝大头）压成 4 比特，而卷积、归一化、embedding 这些对精度敏感、体积又小的模块保留 BF16。我们的职责是**忠实实现**这个混合布局——为此 4 比特和 BF16 两套算子都要写。

**Q：名字是 Qwen3.8，为什么你们代码里叫 qwen35？**
商品名和架构名是两回事。checkpoint 的 config.json 里写的架构标识是 `qwen3_5`（Qwen3.5 这一代的网络结构），发布方基于它训练后以"Qwen3.8"为产品名发布。推理引擎加载时认的是架构标识，所以代码模块按 `qwen35` 命名。类似汽车的"商品名"和"底盘平台代号"的关系。

## 第 3 页 · 成果总览（1.5 分钟）

先给结论，四个数字。

**47 倍**——TTFT 全线提升，1K 是 47.9 倍，16K 是 47.3 倍。[指对比条] 16K 首 token 从 1635 秒到 34.6 秒，就是封面说的 27 分钟到半分钟。

**2.3 倍**——TPOT，8K 上下文从 153 毫秒降到 67 毫秒。

**100%**——200 个混合长短请求的顺序压测全部成功，无 OOM、无 NaN、无 fallback。

**23.5 tok/s**——这是加分项 C4 四路并发的 goodput，官方校准工具跑出来的。

[指徽章行] 下面这排是资格门禁：协议 12/12、公开功能 6/6 精确匹配、hidden 代理集 11/12、七个性能格全部有效、图文探针 4/4。所有数字都来自实测记录，warmup 一次、测五次取中位数，没有估算值。

### 本页可能被问

**Q：TTFT 和 TPOT 分别是什么？**
推理分两个阶段。**prefill**：把整个输入提示词一次算完，产出第一个字——这段耗时就是 TTFT（首字延迟），用户体感是"等多久开始出字"。**decode**：之后逐字生成，每个字的平均间隔叫 TPOT（Time Per Output Token），体感是"出字快不快"。两个阶段瓶颈完全不同：prefill 是算力和访存密集，decode 是显存带宽密集（每生成一个字都要把全部权重从显存过一遍），所以要分开优化、分开汇报。

**Q：47 倍会不会是基线太烂，故意做出来的大倍数？**
基线不是稻草人。它是第一个**通过全部正确性门禁**的版本——协议 12/12、功能 6/6 精确、压测 100%，只是还没做性能优化。而且我们同时给出了绝对尺度：和评测合同给的理论下限比，prefill 还差约 4.8 倍、decode 差约 3.3 倍——我们没有只挑相对倍数说。这两把尺子都写在 REPORT 里。

**Q：CV ≤ 10% 是什么要求？**
CV 是变异系数——5 次测量的标准差除以均值，衡量结果稳不稳。评测合同规定 CV 超过 10% 这格成绩就无效，防止靠运气抖出一个好数。我们七格全部有效，最差一格 8.1%，大多数在 1% 左右——说明性能是稳定复现的，不是偶然。

## 第 4 页 · 第一层：资格与一个关键缺陷（2 分钟）

我们的路线是先拿资格、再谈性能——因为资格是硬门：任何一项可靠性布尔为假，整个提交直接不合格，不是扣分。

[指左侧] 六道门禁的结果都在这里，我重点讲右边这个**真实的缺陷故事**。

压测时我们发现：客户端在一个 8K 请求中途断开后，服务**连续 653 秒**对所有新请求返回 503，但健康检查一直是 200——看起来活着，实际拒绝一切工作。

根因很有意思：流式请求在 prefill 完成前**没有任何字节可写**，而 HTTP 层只能靠"写失败"感知断连——所以取消信号根本无处生效，孤儿请求就一直占着唯一的容量槽跑完为止。

修复分两层：给每个请求配一个 socket EOF 监视线程，一断连立即触发取消；prefill 在**每个块的边界**检查取消信号，中止映射为"已取消"而不是服务故障。[指对比条] 修复后恢复时间从 653 秒降到 **4.86 秒**，并且我们补了 3 个不依赖 GPU 的回归测试——它们在修复前必定失败、修复后全部通过，防止这个缺陷复发。

### 本页可能被问

**Q：hidden 为什么是 11/12？那个失败是 bug 吗？**
先说背景：官方的隐藏测试集不在我们开发机上，所以我们按官方公开集的题型（长文检索、干扰项、多跳、聚合统计）自建了 12 道同格式的代理题，独立随机种子，明确标注非官方。挂的那道是"在 8K 长文里数某类元素的个数"，标准答案 223，模型答 164。我们专门带着逐步 logits 采集重放了它：模型输出错误答案时，第一名和第二名候选词的分差（margin）是 1.125——而我们实现里唯一的数值偏差是"浮点累加顺序不同带来的亚 ulp 级漂移"，那种漂移只能翻转分差**恰好为零**的平局，绝不可能扳动 1.125 的差距。结论：模型是"自信地数错了"——长文计数本来就是大模型的通病，属于模型能力边界，不是我们实现的错。而且资格线是 ≥11/12，达标。

**Q：修复断连会不会误伤慢速客户端？**
不会。触发条件是 socket 读到 EOF（对端正常关闭）或读出错（连接重置），客户端只是读得慢不会触发任何东西。而且取消被映射成"请求已取消"而不是"服务故障"，容量立刻回收、服务健康状态不受影响。这个语义有三个专门的回归测试锁死。

**Q：轨迹（trajectory）是什么？为什么不算门禁？**
轨迹是指：同一个固定输入，你的实现生成的 token 序列和参考实现（vLLM）逐字对比能匹配多长。合同把它定为 5 分的软目标、阈值为 0——因为它有个数学死角：参考实现自己在某几步的第一、二名 logits **完全相等**（分差恰好为 0），这种平局怎么选取决于浮点累加顺序，任何优化只要改变累加顺序就可能翻转它，没有容差能修。我们最终版本反而把匹配长度从 28 提到了 76 个 token。

## 第 5 页 · 第二层：性能的下降路径（2 分钟）

资格拿到后做性能。方法是**单变量配对实验**：一次只改一个东西，改前改后跑同样的负载，correctness 不降、变异系数不超 10%、端到端收益超过噪声才接受。一共做了 **17 次，9 项接受、8 项拒绝**——拒绝的每一项也保留了数据和根因。

[指瀑布图，从左往右] 16K 首 token 的下降路径是这样的：

1635 秒的调试基线，第一刀是 **W4 GEMM**——prefill 阶段不再逐行解量化，而是把权重解压一次交给 tensor core 做矩阵乘，降到 711 秒；

第二刀 **scratch 池化**，把反复的大块显存分配换成按尺寸复用的池子，488 秒；

第三刀把 **prefill 分块从 64 提到 512**，摊薄每块的固定开销，409 秒；

最后一刀是**行协作 softmax**，直接砍到 34.6 秒——这一刀是整个项目最大的单点收益，值得单独讲一页。

### 本页可能被问

**Q：GEMV 和 GEMM 什么区别？为什么换成 GEMM 就快了？**
GEMV 是"矩阵乘向量"（一次算一行输入），GEMM 是"矩阵乘矩阵"（一次算一批输入）。decode 阶段每次只有一个新 token，天然是 GEMV；但 prefill 一次进来几百上千个 token，本该用 GEMM 批量算。旧实现把 prefill 也当成一行行的 GEMV：每行都独立地把 4 比特权重现场解压一遍——等于同一个权重矩阵被从显存反复搬运几十次。改成"先把权重解压一次成 BF16，再用 GPU 的 tensor core（矩阵乘专用硬件单元）一次算完整批"，权重只搬一遍，所以 TTFT 直接降了 74%。

**Q：被拒绝的八项都是什么？为什么值得一提？**
包括：延迟状态检查（预测能省 200 次同步，实测零收益——那些同步不在关键路径上）；五个 decode GEMV 微优化（最好的只快 1.8% 在噪声内，最差的反而慢 54%，每个都做了汇编级分析找到根因）；一个查表方案在设计阶段就被成本分解否决；还有一次是我们自己初判太保守、复核显存后反而采纳了。值得一提是因为**负结果防止重复踩坑**，而且证明我们的接受标准是真门槛——不是什么都往上堆。

**Q：纵轴为什么用对数刻度？**
数据从 1635 到 34.6 跨了两个数量级，线性刻度画出来后面几根柱子根本看不见。柱顶的数值标签是精确值。

## 第 6 页 · softmax 的 512 倍冗余（2.5 分钟）

[指代码条] 就是这一行循环。它在旧 kernel 里被 block 内**每一个线程**完整执行一遍。256 个线程做完全相同的全行扫描，再乘上每行的块数——**每一行被从头到尾扫了 512 次**，而正确做法只需要两遍。

有意思的是找到它的过程，我的判断被数据推翻了三次：

第一次，用单层模型估算只能解释 408 秒里的 124 秒——于是改用逐块递增 KV 的"阶梯测量"，发现单个注意力层就要 25 秒，16 层正好约 400 秒，问题锁定在注意力；

第二次，我怀疑是矩阵乘的形状退化，把 M 从 6 重排成 512——只降了 6%，不是主因；

第三次怀疑输出步长，微基准显示单次矩阵乘只有 5.7 微秒，跟步长无关；

最后发现**错的是我自己的测量口径**：之前测 softmax 用了 kv_offset=0，平均只扫 256 列，而真实调用要扫一万五千多列。按真实列数换算是 2234 毫秒，和实测的 2082 毫秒对上了——softmax 占注意力 prefill 的 98%。

[指右图] 修复方案：一行一个 block，256 个线程分段扫描、shared memory 里树形归约。单层从 23.06 秒降到 **0.659 秒，35 倍**；服务端 16K 首 token 在配对实验里从 408.7 秒降到 31.9 秒，最终配置的正式五次中位数是 34.6 秒。修复后公开功能六个测例重新全部精确通过。

### 本页可能被问

**Q：先解释一下，softmax 在注意力里干什么？为什么会有"扫描整行"？**
注意力算每个字对其他字的"关注度"：先算出一行分数，然后 softmax 把这行分数归一化成概率。softmax 需要两个全行信息——行最大值（防止指数溢出）和指数和（做分母），所以必须扫整行。正确做法是 256 个线程**分工**：各扫自己那 1/256 段，再用 shared memory（GPU 上一小块线程间共享的高速缓存）把局部结果合并——总共相当于扫两遍。旧代码错在每个线程都独立扫**完整**一行，256 个线程重复 256 遍，每行又被多个 block 覆盖，合计 512 倍冗余。短文本时这行只有几百列、浪费不明显；16K 时一行一万六千列，就成了 98% 的耗时。

**Q：改了求和顺序，结果还对吗？**
分两半看。求最大值与顺序无关，结果一个比特都不变。指数求和从"一个线程串行加"变成"分段再树形合并"，浮点加法不满足严格结合律，所以结果可能在最后一两个比特上有差异——这叫"重结合漂移"，和我们已接受的 GEMM 优化是同一类、同一量级。验证上：修复后六个公开功能测例重新**逐字精确**通过；而这种比特级漂移理论上只可能影响前面说的"分差恰好为零的平局"。

**Q：31.9 秒和别处的 34.6 秒为什么不一样？**
测量口径不同。31.9 是配对实验的探针读数（热身 1 次 + 测 3 次），专门用来同口径对比"这一项改动"的前后；34.6 是最终配置的正式战役中位数（热身 1 + 测 5，CV 达标），是对外的权威数字。配对实验必须用自己的前后对比，所以这页写 31.9；成绩页一律用 34.6。

## 第 7 页 · 两个"非计算"瓶颈（2 分钟）

另外两个大瓶颈也都不在算术里。

[指左图] 第一个：W4 投影的旧 kernel 是一个 block 算一个输出元素，每个 block 自己去读权重。prefill 一块 64 行，等于**把整个权重矩阵从显存搬了 64 遍**——批处理效率只有 1.03 倍，几乎等于没有批处理。修复就是刚才说的解量化一次、交给 tensor core：1K 首 token 从 77 秒到 20 秒。

[指甜甜圈] 第二个更隐蔽：微基准显示，分配加释放一块 178 MB 的临时缓冲要 **3.22 毫秒**，占一次完整 MLP 投影的 82%。每层每块要做 7 次投影、各自分配一次——算下来 **prefill 的八成时间花在显存页表操作上**，GPU 根本没在算数。改成按尺寸复用的 scratch 池后，1K 首 token 从 19.9 秒降到 5.76 秒，而且冻结请求的输出**逐位不变**——这类改动我们都要求位级等价。

### 本页可能被问

**Q：cudaMalloc 分配显存为什么这么慢？**
显存分配不是改个指针那么简单：驱动要建立页表映射（把虚拟地址映射到物理显存页），大块分配还带一次隐式的设备同步——GPU 上所有在飞的工作要先排空。178 MB 一次 3.22 毫秒是我们实测的。频繁"分配-用完-释放"就是在反复交这笔税。解法是池化：这几种固定尺寸的缓冲各留一块常驻复用，热路径上零分配。

**Q：解压权重和池子不是都要额外显存吗？账怎么算的？**
是的：解压 scratch 约 170 MB（双缓冲 340 MB），池子整体常驻约 460 MB。所有这些都登记进 admission（准入）的显存账本——服务启动时按最坏情况估算总需求，超过物理显存就**直接拒绝启动**（fail closed），而不是跑到一半 OOM。实测峰值 19958 MB，离 24564 上限还有约 4.5 GB。

**Q：这页的池子和后面 C4 页的"流序分配"是一回事吗？**
不是，两处各用了合适的工具。prefill scratch 是固定几种尺寸、每次用完即可复用——用常驻池，热路径零分配。C4 的会话状态是几百块零散缓冲、生命周期跟着请求走——用 CUDA 的流序分配器（cudaMallocAsync），分配释放排进 GPU 指令流里异步做，冷启动从 330 毫秒降到个位数毫秒。

## 第 8 页 · 实验方法（1.5 分钟）

这些结论为什么可信，靠四条纪律。

**四卡并行**：正式测量永远独占指定那张卡、带全局锁；另外三张卡跑归因和测试分片，一轮验证从 35 秒压到 12 秒——快了才愿意多测。

**三变体微基准**：给 W4 kernel 做了"只读权重、去掉解量化、完整"三个诊断变体，一次跑出成本分解——访存 41%、乘加 21%、解量化算术 39%，并且证明访存已达峰值带宽的 81%。之后不再猜瓶颈，只看归因。

**先证位相等再写 kernel**：比如 Marlin 位技巧动工前，先穷举验证了位构造和生产路径数学上必然一致——正确性由证明保证，不靠事后调容差。

**双卡双副本复测**：任何低于 5% 的收益必须在两张卡各跑两份。这条纪律实际排除过一次 4% 的假阳性——卡间差异 2.4%，比候选效应还大。

### 本页可能被问

**Q：用四张卡，不是说好单卡吗？**
合同约束的是**服务和正式成绩**必须单卡：所有对外数字都在指定 UUID 的那张卡上、拿全局文件锁独占跑出来的。另外三张卡只在开发期用来并行跑测试分片和性能归因——相当于工人多了，但考场只有一个。这个使用方式是获得授权的，REPORT 里有说明。

**Q："先证位相等"具体怎么证？**
举例：有个优化想用位运算技巧替代数值转换——把 4 比特整数 q 直接拼进 BF16 的位模式（0x4300|q 恰好等于 128+q）。动工前我们穷举了全部 16 个 q 值验证拼法精确、全部 256 对 (q,z) 验证减法在 BF16 下无舍入、再证明乘积有效位数不超过 FP32 能精确表示的范围——三步下来数学上保证和原路径**每个比特都相同**，不需要事后靠放宽容差来"混过"测试。（顺带一提：这个技巧位相等成立，但实测慢 54%，被拒了——正确性证明和性能收益是两回事。）

**Q：那次假阳性具体怎么回事？**
一个 GEMV 微优化首轮在三张卡上测出约 4% 收益。按纪律复测：同一候选在两张卡各跑两份，结果基线两份 923/901 微秒、候选 934/913 微秒——**两张卡之间的固有差异 2.4% 比候选效应还大**，把卡间差异当成了优化收益。修正后候选实际慢 1.3%，拒绝。从那以后所有低于 5% 的结论必须双卡双副本。

## 第 9 页 · bonus 1：多模态（2 分钟）

第一个加分项，图文多模态。[沿流水线指] 我们的原则是**每一站都要有可验证的判据**：

PNG 进来，预处理和 HuggingFace 处理器**逐位一致**——120 万个浮点数零差异；prompt 构造 token 级精确一致；27 块 vision 塔移植到 CUDA，最终融合嵌入和 FP32 参考的余弦相似度 **0.99972**；196 个图像嵌入精确散射到 image_token 的位置；最后 LLM 生成——四个合同类别的自建探针 **4/4 全对**，比如七段数码管图片正确读出 "382"。

同样重要的是**不伤文本**：图文混合压测 36/36；冻结的文本请求在多模态服务上的输出**逐字节不变**；整个能力挂在一个环境变量后面，不开就是纯文本提交件，默认按合同 fail closed。

### 本页可能被问

**Q：多模态的原理是什么？图片怎么进语言模型？**
图片先切成 16×16 的小块（448×448 的图切成 784 块），每块变成一个向量，过一个 27 层的"视觉塔"（小型 transformer）提特征，再经过 merger 压缩成 196 个和文字 embedding 同维度（5120）的向量。prompt 里预留了 196 个特殊的图片占位 token，我们把这 196 个视觉向量**精确写到占位 token 对应的位置**上——之后语言模型把它们当作"看得见的词"一起处理，就能回答图片问题了。

**Q：余弦 0.99972 是什么意思？为什么不像文本那样位相等？**
余弦相似度衡量两个高维向量的方向差异，1.0 是完全同向。我们的塔用 BF16 算，参考实现用 FP32，27 层下来舍入误差会累积，逐元素比对会有 1-8% 的漂移——这是精度格式决定的，不是实现错误。关键有两点：一是能位相等的环节全都位相等了（预处理 120 万个数零差异、prompt 逐 token 一致、新 kernel 在标准尺寸下和旧 kernel 逐位一致）；二是塔的出口有个 LayerNorm 会重新归一化，所以**方向**才是决定性的——0.99972 说明方向几乎没变。端到端 4/4 全对是最终验证。

**Q：探针是你们自建的，怎么证明不是挑了容易的？**
探针严格按照评测合同的规格构造：448×448 PNG、四个规定类别各一道（数码管读数、空间颜色、柱状图算术、数数）、同样的请求格式，答案在生成图片时就确定。它验证的是**整条管道的正确性**；官方图片集在评测平台手里，正式得分由平台跑——我们不声称那部分分数，PPT 和报告里都写明了。

## 第 10 页 · bonus 2：C4 四路并发（2 分钟）

第二个加分项，C4 并发。[指流图] 架构是批式 protocol runtime：admission 发 4 个许可，单个 batch worker 持有模型，每轮做**一步批式 decode**、四路各出一个 token。

三个关键点：批式 GDN 和 RoPE kernel 的结果与串行路径**逐字节一致**，用真实权重的回归测试守护；曾经出现的 503 竞态定位到一个 17 微秒的窗口——许可释放晚于响应发送——用两阶段交付修掉，之后 32 个请求零 503；性能上靠 prefix cache（相同 prompt 直接从模板 fork，2 毫秒）和流序显存分配（冷启动 fork 从 330 毫秒降到个位数毫秒）。

[指记分卡] 这一项是**官方 evaluator 校准工具**验的：成功率和正确率 1.0、Jain 公平性 0.9993、p95 首 token 和每 token 延迟都在门槛内、goodput 23.53 tok/s——全部效度门通过。

C8 我们没有交付，原因量化得很清楚：8 份完整请求状态需要 4.1 GiB，超出 2.36 GiB 的准入预算；共享 scratch 的改造路径已经算清但没来得及实现，所以如实不声称。

### 本页可能被问

**Q：C4 是什么意思？goodput 和普通吞吐有什么区别？**
C4 = 4 个客户端闭环并发：每个客户端发一个请求、等完整收到响应再发下一个，四路同时进行，共 32 个请求。goodput 是"**有效**吞吐"——只有答案正确的请求才计入产出，分母是整批的完成时间。也就是说答错、超时、失败都白干，防止"快但错"刷分。

**Q：Jain 公平性 0.9993 是什么？**
Jain 指数衡量多个并发客户端被服务得是否均匀，1.0 表示四路完全平等，最低 0.25 表示只有一路被服务。合同要求 ≥0.95。我们 0.9993，说明调度器没有饿死任何一路——每轮批式 decode 给四路各出一个 token，天然公平。

**Q：批式和串行怎么保证结果一致？**
批式 kernel 的设计是"每请求一个独立线程块 + 各自的状态指针"，核心计算逐行复制自串行 kernel，只是外面多了一层批索引——每个请求内部的计算顺序完全没变。验证是硬的：用真实模型权重跑多步"批式 vs 串行"，断言输出和内部状态**逐字节相等**。只有两处矩阵乘的堆叠属于文档化的重结合（和前面同类），已记录。

**Q：C8 和 MTP 为什么不做？**
都卡在客观约束且都量化过。C8：8 份完整请求状态要 4.1 GiB，准入预算只有 2.36 GiB；解法（8 个会话共享 GDN 临时缓冲，每份从 443 MB 降到 295 MB）已经设计并算清账，但没来得及实现，所以不声称。MTP（投机解码）：要让矩阵乘硬件吃饱需要一次验证 7 个以上草稿 token，而草稿接受率撑不到那个深度；且它需要给 48 层 GDN 状态做事务回滚，是正确性风险最高的改动——评估后放弃，理由写在 REPORT。

## 第 11 页 · 取舍与边界（1 分钟）

四组取舍，讲一组最典型的：优化改变浮点累加顺序，会翻转参考轨迹里 margin 恰好为零的平局——我们用 5 分的轨迹软目标换 35 分的 TTFT 主轴，因为数学上任何容差都修不了 margin 为零的平局，而公开功能始终 6/6。

右边是我们**主动不声称**的：没有平台 scorer 产物就不声称任何得分；hidden 和图片集是自建代理、已标注非官方；no_xid 是间接证据；C8 和 MTP 未交付。宁可少说，不说过头。

### 本页可能被问

**Q：no_xid 是什么？为什么是"间接证据"？**
Xid 是 NVIDIA 驱动在内核日志里记录的 GPU 错误码（如显存崩溃、通信超时），可靠性要求全程无 Xid。但开发机的内核日志（dmesg）没有读取权限，我们无法直接看——所以改用间接证据：服务日志全程零 CUDA 错误、压测后显存精确回落到基线、其他卡计数稳定。我们在报告里明确标注这是间接证据，而不是装作查过内核日志。

**Q：你们这么多"不声称"，到底预期拿多少分？**
如实回答：正确性、可靠性的证据链是齐的，两个 bonus 一个过了官方校准、一个有位级证据；但动态性能分按同轮最优参考计，多模态私有分要平台跑官方图片集——这些不在我们手里。我们的策略是把**每一分对应的证据**都交齐、可复验，分数交给评测流程。

### 本页可能被问

**Q：验收 SHA 是什么？为什么它能作为验收标准？**
git 的每次提交都有一个由全部代码内容算出的哈希值（SHA），内容差一个字节哈希就完全不同——所以它是代码状态的唯一指纹。写明验收 SHA = 06993a2，意思是"评审请以这个指纹对应的代码为准"，任何人 checkout 这个提交，看到的和我们提交的逐字节一致，无法事后偷改。

**Q：现场验证要多久？**
`test.py check` 约 45 秒（校验合同哈希、模型文件、依赖完整性）。起服务约 8 分钟——权重要做完整性摘要校验、载入 19.5 GB、再热身，期间端口未绑定是正常现象。起来之后冻结协议 gate 几十秒跑完，预期 12/12。
